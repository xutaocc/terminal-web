# Web Terminal 部署与使用指南

适用于 Ubuntu Linux、Windows WSL Linux 环境、macOS，以及**原生 Windows**。原生 Windows 用 psmux（Windows 原生的 tmux 替代品）代替 tmux，安装和启动方式与其他平台不同，见第 10 节「原生 Windows 部署」，文件管理页面等少数功能在 Windows 上暂不可用。浏览器客户端可以使用 Windows、macOS 或手机等设备。

本文对应包含共享 Token 认证功能的 `xt-dev261011-f-main` 分支；原生 Windows 支持在 `win-f-remote-hosts` 分支。

## 1. 环境依赖

启动前需要准备：

- **Node.js 和 npm**：建议使用 Node.js 22。已有其他版本可以先尝试安装和运行；若遇到依赖安装或兼容性报错，再尝试 Node.js 22。项目声明最低版本为 Node.js 18。
- **tmux**：必需，用于终端会话、断线恢复和历史滚动。macOS 建议使用 **3.8**，Ubuntu Linux（含 WSL Ubuntu）建议使用 **3.4**。这些是建议版本，不是强制要求；已有其他版本且能正常使用时直接复用，不重复安装。
- **Git**：用于获取和更新项目，优先使用系统已有环境。
- **Python 3**：安装 node-pty 原生依赖时可能需要，优先使用系统已有环境。
- **编译工具**：安装 node-pty 原生依赖时可能需要。

请先确认已有 Git 和 Python 3 可用，无需重复安装或另装不同版本。本文不提供它们的安装步骤。

Tailscale、EasyTier 和 tmux 恢复插件均为可选依赖，普通局域网使用无需安装。

先检查 tmux 是否可用：

```bash
command -v tmux
tmux -V
```

检查成功即可复用现有 tmux，跳过下面的 tmux 安装步骤。自定义目录中的 tmux 也可以复用，只需确保服务的 PATH 能找到它；无需为了本项目另装一份。

### tmux 版本建议与复用原则

| 部署环境 | 建议版本 |
| --- | --- |
| macOS | tmux 3.8 |
| Ubuntu Linux / WSL Ubuntu | tmux 3.4 |

以上版本供新环境准备和兼容性排查时参考，不代表其他版本不能使用：

- **已有 tmux**：先使用现有版本部署和运行。运行正常时，无需重新安装、升级或降级到建议版本。
- **尚未安装 tmux**：再按下方步骤安装。包管理器提供的版本可能与建议版本不同，可以先尝试运行，不要求为对齐版本而额外安装一份。
- **出现 bug 时**：先记录 `tmux -V` 和 `command -v tmux` 的结果，检查服务 PATH、tmux 配置及相关日志；若仍怀疑版本兼容性，再考虑使用对应系统的建议版本复现和排查。

### Ubuntu / WSL Linux

仅在缺少 tmux 时执行以下命令，适用于 Ubuntu、Debian 及 WSL 中的 Ubuntu：

```bash
sudo apt update
sudo apt install -y tmux
```

编译工具也优先复用已有环境；仅在安装原生依赖时提示缺少编译工具，才补充：

```bash
sudo apt install -y build-essential
```

其他 Linux 发行版同样先检查已有依赖，仅在缺失时通过相应包管理器安装。

### macOS

仅在缺少 tmux 且已安装 Homebrew 时：

```bash
brew install tmux
```

如果安装依赖时需要编译工具，且系统中尚未提供：

```bash
xcode-select --install
```

Node.js 和 npm 请按自己的常用方式准备，不要求特定版本管理工具。安装后检查：

```bash
node --version
npm --version
tmux -V
git --version
python3 --version
```

## 2. 获取代码与安装

在 Linux 或 macOS 终端中执行：

```bash
git clone --branch xt-dev261011-f-main https://github.com/xutaocc/terminal-web.git
cd terminal-web
npm ci
npm run build
```

已有项目则进入实际目录，无需重新克隆。不要跨系统复制 `node_modules`，应在目标系统重新安装。

安装时保留开发依赖，不要使用 `--omit=dev`：当前启动需要 tsx，构建需要 esbuild。

## 3. 配置与启动

首次配置时复制模板，已有 `.env` 则直接编辑，避免覆盖：

```bash
cp .env.example .env
```

局域网使用可在 `.env` 中设置：

```dotenv
HOST=0.0.0.0
PORT=8090
DEFAULT_SESSION=web
```

`0.0.0.0` 表示监听所有 IPv4 网卡；仅供本机使用可改为 `127.0.0.1`。浏览器访问时使用服务器实际 IP，不使用 `0.0.0.0`。

启动：

```bash
bash scripts/start.sh
```

脚本自动加载 `.env`，启动后打印 Token 和各网卡对应的带 Token 访问链接。未监听的地址会标注说明。

也可以直接指定配置启动：

```bash
HOST=0.0.0.0 PORT=8090 npm start
```

注意：`npm start` 本身不会自动加载 `.env`。前台运行使用 `Ctrl+C` 停止。

## 4. 登录与使用

打开普通地址，在 Web Terminal 登录页输入 Token：

```text
http://SERVER_IP:8090/
```

或者使用启动日志打印的完整链接：

```text
http://SERVER_IP:8090/?token=YOUR_TOKEN
```

将示例中的 IP 和 Token 替换为实际值。链接登录成功后会自动移除地址中的 Token。

默认 Token 文件：

```text
~/.config/terminal-web/auth-token
```

首次启动生成，后续重启继续使用同一个 Token。可在服务器终端查看：

```bash
cat ~/.config/terminal-web/auth-token
```

可选的 `AUTH_TOKEN_FILE` 用于指定保存路径；非空 `AUTH_TOKEN` 环境变量优先覆盖文件中的 Token。正常使用无需设置它们。

使用规则：

- 所有页面、API、文件接口和终端连接均要求认证，包括局域网访问。
- 登录凭据保存在 HttpOnly Cookie 中，多个设备可同时登录，不会互踢。
- 服务端没有登录超时；浏览器清除 Cookie、保存期限结束或隐私窗口关闭后，可能需要重新登录。
- “退出登录”只退出当前浏览器及同源标签页，不影响其他设备，也不结束 tmux 中的任务。
- 关闭网页、断网后可以重新连接原会话；**关闭会话 `×` 或重启会话会终止其中的程序**。
- 多设备连接同名会话时共享同一个终端；可通过 `/?session=work` 指定会话。

## 5. 后台运行

先停止同端口的前台实例，再在项目目录安装服务：

```bash
HOST=0.0.0.0 PORT=8090 bash scripts/service.sh install
```

Linux 使用 systemd 用户服务，macOS 使用 launchd 用户服务。WSL 中使用此方式的前提是已有可用的 systemd。

常用操作：

```bash
bash scripts/service.sh status
bash scripts/service.sh logs
bash scripts/service.sh restart
bash scripts/service.sh uninstall
```

后台服务安装器不会加载 `.env`；HOST、PORT 等支持的配置应在安装命令中传入。其他配置需要调整生成的服务文件。修改 `.env` 不会自动改变后台服务。

后台服务的 PATH 与交互终端可能不同，特别是 macOS Homebrew 路径。前台正常、后台提示找不到 tmux 时，将 `command -v tmux` 对应目录加入服务配置的 PATH。

Linux 的开机启动取决于 systemd 用户服务及 linger 配置；macOS 用户服务通常在用户登录后启动；WSL 服务需要 WSL 实例保持运行。

## 6. 更新与重置 Token

更新前确认没有需要保留的未提交修改：

```bash
git pull --ff-only
npm ci
npm run build
bash scripts/service.sh restart
```

未安装后台服务时，最后一步改为重新执行 `bash scripts/start.sh`。

需要更换 Token 时：先停止服务，删除当前 Token 文件，再启动。新 Token 会自动生成，所有设备需要重新登录。如果设置了非空 `AUTH_TOKEN`，应更改该环境变量，而不是仅删除文件。

## 7. PC 端侧栏：文件夹与目录卡片

电脑浏览器（窗口宽度大于 640px）左侧有会话侧栏，手机上不显示。侧栏分三层：

```text
▾ 📁 文件夹            ← 你建的分组，只有名字，和目录无关
    ▸ 目录卡片         ← 文件夹里同一工作目录的会话自动合成一张
        [会话] [会话]  ← 会话 chip，点击切换
▾ 未分组               ← 还没放进任何文件夹的会话（灰色小字，固定在最后）
```

一个文件夹都没有时，不显示"未分组"标题，卡片直接平铺。

### 文件夹

- 新建：点侧栏顶部"会话"右侧的文件夹 + 按钮，输入名称，再接着新建这个文件夹的第一个会话。中途取消则文件夹和会话都不创建，所以不会出现空文件夹。
- 会话归属由你决定：在哪个文件夹里新建就属于哪个；在会话里 `cd` 到别的目录，它仍留在原文件夹，只是会挪到对应目录的卡片里。
- 把已有会话放进文件夹：拖动会话 chip 或整张目录卡片到文件夹上；或在 chip / 卡片上右键，选"移到「X」"或"移出文件夹"。
- 重命名：鼠标悬停在文件夹标题上，点铅笔图标，或双击名称；回车保存，Esc 取消。
- 悬停文件夹标题时的 `+`：在这个文件夹里新建会话。
- **文件夹不能直接删除**。里面的会话全部关闭或移出后，文件夹自动删除：
  - 在本设备关闭最后一个会话：关闭确认框里会提示"这是文件夹「X」里最后一个会话，关闭后该文件夹也会删除"。
  - 拖出或移出最后一个会话：先弹出确认。
  - 最后一个会话在别的设备上被关闭，或程序自己退出：文件夹自动删除，页面提示"文件夹「X」已无会话，已删除"。
- 点文件夹标题可以折叠或展开（每台设备分别记住）。

### 目录卡片

- 同一个文件夹里、工作目录相同的会话合成一张卡片，标题默认是目录名，下面一行是路径。同一个目录可以出现在不同的文件夹里。
- 重命名：悬停卡片点铅笔图标，或双击卡片名称。只改显示名，不改真实目录；改回目录原名即恢复默认。名称按文件夹分别记，同一目录在不同文件夹里可以叫不同的名字。
- 拖动整张卡片到别的文件夹，卡片里的会话一起移过去。目标文件夹里已经有相同目录的卡片时自动合并，名称以目标文件夹里的为准；目标里没有时，你起的名字会跟着带过去。
- 悬停卡片时的 `+`：在这个目录、这个文件夹里新建会话。
- 点卡片空白处：切到你上次在这个目录用过的会话。

### 顶部标签栏与其他操作

侧栏展开时只显示当前文件夹里、与当前会话同一目录的会话；收起侧栏（侧栏左上角或底部的收起按钮）或在手机上时，显示全部会话。

拖动侧栏右边缘调整宽度（双击恢复默认）；底部按钮依次是设置、帮助、定位到当前会话、收起侧栏。

文件夹、会话归属和卡片名称保存在服务端 `~/.terminal-web/projects.json`，所有设备共用；侧栏宽度、是否收起、折叠状态由各设备分别记住。会话关闭后，其归属记录自动清除。

## 8. 会话状态显示与 Agent 钩子

标签、侧栏卡片和手机端的圆点显示每个会话里 AI agent（Claude Code、Codex、qwen-code、Kimi Code、opencode、MiMo Code）的状态。状态由服务端统一判断，所有设备看到的一样，没打开过的标签也有状态：

| 圆点 | 含义 |
| --- | --- |
| 橙色闪烁 | 等待你确认（权限确认或 agent 提问） |
| 绿色转圈 | 执行中 |
| 亮绿色 | 已完成，未读（标签同时带淡橙色底） |
| 暗绿色 | 已完成，已读 |
| 灰色 | 空闲 |

切到某个会话并在浏览器里看着它时，它自动变成已读。页面标题前的数字是需要你处理的会话数（等待确认 + 未读）。

### 状态来源（设置面板）

在页面右上角 `⋯` 打开设置面板，在"状态来源"一行切换，立即生效，所有设备共用（保存在服务端 `~/.terminal-web/agent-status.json`）。未选择过时默认为钩子，默认值写在 `src/agent-status.ts` 的 `DEFAULT_AGENT_STATUS_MODE`：

| 值 | 说明 |
| --- | --- |
| 钩子 `hooks`（默认） | Claude Code / Codex 通过钩子主动上报每一轮的开始、等待确认、结束，最准确。还没上报过的会话自动按屏幕识别规则判断 |
| 屏幕识别 `screen` | 不用钩子。服务端每秒通过 tmux 读取各会话屏幕，按下方"屏幕识别支持的 agent"表里各 agent 的固定字样判断执行中、等待确认和完成 |
| 原始 `legacy` | 原始逻辑：浏览器按回车后屏幕有变化就转圈 60 秒，只跟踪当前页面打开过的标签，状态不跨设备 |

### 屏幕识别支持的 agent

屏幕识别只认下表中 agent 的**精确字样**，不做泛化匹配；屏幕上匹配不到任何规则时保持原状态不变。只看屏幕底部若干行，正文里出现相同字样不会被误判。"等待确认"必须同时出现提问文字和选择菜单。

| Agent | 执行中 | 等待确认 | 空闲（回到提示符） |
| --- | --- | --- | --- |
| Claude Code | 状态栏 `· esc to interrupt` | 确认提问 + `❯ 1. Yes` 编号菜单 | `❯` 提示符 |
| Codex | 状态栏 `(12s • esc to interrupt)` | `Would you like to …` + `› 1. Yes, proceed` | `› Ask Codex to do anything` |
| qwen-code | 状态栏 `(12s · esc to cancel)`，或 `Press Esc again to stop` | `Do you want to proceed?` / `Apply this change?` / `Allow execution of: '…'?` + `› 1. Yes, allow once` | `›` 提示符 |
| Kimi Code | `Press Esc again to interrupt` | `Approve once` / `Approve for this session` 编号菜单 | 方框输入框 `│ >` |
| opencode | 底部行以 `esc interrupt` / `again to interrupt` 结尾 | `△ Permission required` + `Allow once … Reject … enter confirm` 按钮行 | 底部 `tab switch mode` 或 `/ commands` |
| MiMo Code | 同 opencode（基于 opencode 的分支） | 同 opencode | 同 opencode |

已知限制：

- Kimi Code 执行中的常规状态行没有固定字样，屏幕识别只能认出"按过一次 Esc"和"等待确认"两种状态；需要准确的执行中显示请用钩子。
- qwen-code、opencode、MiMo Code 的规则取自各自源码中的界面文案，尚未在本项目中实机验证；界面文案随版本变化时可能需要更新 `src/agent-status.ts` 中的规则。
- 不在上表中的 agent（以及普通 shell 里的长命令）屏幕识别不认，状态保持空闲；需要时切换到"原始"方式。
- 新增或修改规则时，在 `tests/agent-status.test.ts` 中补充对应的界面样例（含正文误判的反例），运行 `node --import tsx --test tests/agent-status.test.ts`。

### 钩子模式下的兜底

钩子模式下，屏幕规则仍在兜底：agent 进程退出时状态回到空闲；Claude 按 Esc 中断不会触发结束钩子，屏幕回到输入提示符 6 秒后判为完成。屏幕被全屏界面（如消息查看浮层）遮住时，保持原状态不变。

### 安装钩子（钩子方式需要）

目前一键安装支持 **Claude Code 和 Codex**。qwen-code、Kimi Code、opencode、MiMo Code 暂未接入钩子，这几个 agent 的状态由上面的屏幕识别规则兜底判断。

前提：服务已在运行，本机有 `curl`，agent 在本服务的 tmux 会话里运行。在项目目录执行：

```bash
node scripts/install-agent-hooks.mjs
```

安装器做的事：

- 把 `scripts/agent-hook.sh` 复制到 `~/.terminal-web/agent-hook.sh`，并在 `~/.terminal-web/agent-hook.env` 写入服务地址和 Token 文件路径。服务地址自动探测：`.env` 的 HOST/PORT、`127.0.0.1`、Tailscale IP，取第一个能访问的。
- Claude Code：在每个配置目录的 `settings.json` 里追加钩子。包括 `~/.claude`、`$CLAUDE_CONFIG_DIR`，以及用过的 `~/.claude-*` 目录（例如通过 `CLAUDE_CONFIG_DIR=~/.claude-relay claude` 使用的中转配置）。
- Codex：在 `~/.codex/hooks.json`（或 `$CODEX_HOME`）追加钩子，并在 `config.toml` 写入对应的信任条目，Codex 不会再弹出钩子信任确认。
- 只增删自己的条目（命令里含 `/.terminal-web/agent-hook.sh` 的），不改动其他工具的钩子；每个被修改的文件第一次修改前备份为 `<文件>.bak-terminal-web`。重复执行是安全的。

**已经在运行的 Claude Code / Codex 会话需要重启后才会加载钩子。**

其他用法：

```bash
node scripts/install-agent-hooks.mjs --check        # 检查安装状态和服务连通性，全部正常时退出码为 0
node scripts/install-agent-hooks.mjs --uninstall    # 移除全部钩子
node scripts/install-agent-hooks.mjs --only=claude  # 只处理 Claude Code（或 --only=codex）
node scripts/install-agent-hooks.mjs --url=http://127.0.0.1:8090        # 手动指定服务地址
node scripts/install-agent-hooks.mjs --claude-dir=~/.claude-relay       # 手动指定 Claude 配置目录，可重复
```

钩子脚本不影响 agent：始终立即返回、退出码为 0，后台以 2 秒超时上报；不在 tmux 里运行、服务没启动或 Token 读不到时什么都不做。

### 交给 AI agent 自动安装

可以把下面这段直接交给 Claude Code / Codex 执行：

> 在 terminal-web 项目目录中为本机安装 agent 状态钩子：
> 1. 运行 `bash scripts/service.sh status` 确认服务在运行；没在运行就先按本文第 3 或第 5 节启动。
> 2. 运行 `node scripts/install-agent-hooks.mjs`，查看输出中的"Hooks report to …"一行，确认显示 `server reachable, mode: hooks`。若显示 `NOT reachable`，用 `--url=http://<实际地址>:<端口>` 重新运行。
> 3. 运行 `node scripts/install-agent-hooks.mjs --check`，退出码必须为 0，且 Claude Code 每个配置目录都是 `10/10 hooks`、Codex 为 `6/6 hooks`（未安装 Codex 时显示 0/6 属正常，可加 `--only=claude` 再检查）。
> 4. 告诉用户：已经在运行的 Claude Code / Codex 会话需要重启才生效。不要自行重启用户的 agent 会话。

验证效果：在 terminal-web 的某个会话里启动 Claude Code 并发一条消息，该标签的圆点应立即开始转圈，回复结束后变成亮绿色（若你正在看这个标签，则直接变成暗绿色）。

## 9. 注意事项与排查

| 问题 | 检查方向 |
| --- | --- |
| 无法创建终端 | 确认 tmux 已安装，并在服务 PATH 中 |
| 怀疑 tmux 版本兼容性导致异常 | 先检查现有版本、服务 PATH、配置和日志；排查后再考虑 macOS 使用 3.8、Ubuntu / WSL Ubuntu 使用 3.4。运行正常时无需更换现有版本 |
| npm 安装失败 | 检查编译工具、Python 3；已有其他 Node.js 版本可先尝试，遇到兼容性问题再使用 Node.js 22 |
| 端口已占用 | 停止重复实例，或修改 PORT |
| 本机可访问，其他设备不可访问 | 检查 HOST、真实 IP、防火墙及路由；WSL 还需确认网络转发或镜像网络配置 |
| 未登录返回 401 | 正常现象，输入 Token 或使用完整登录链接 |
| Token 文件为空或不可读取 | 检查服务用户、路径和权限；按重置流程处理 |
| 侧栏不显示 | 侧栏只在电脑浏览器、窗口宽度大于 640px 时显示；若已收起，点顶部标签栏左侧的展开按钮 |
| 顶部标签栏少了会话 | 侧栏展开时标签栏只显示当前文件夹、当前目录的会话；从侧栏切换，或收起侧栏查看全部 |
| 文件夹突然不见了 | 里面的会话都已关闭（含在其他设备上关闭或程序退出），文件夹随之删除，属正常行为 |
| 状态圆点一直灰色 | 执行 `node scripts/install-agent-hooks.mjs --check`；确认已重启 agent 会话；确认设置面板中"状态来源"不是"原始" |
| 执行完成后一直转圈 | 钩子模式下 6 秒内会被屏幕规则纠正；若长期不变，检查该会话屏幕底部是否被全屏界面遮住 |
| 某个 agent 状态不对（qwen-code / Kimi / opencode / MiMo 等） | 对照"屏幕识别支持的 agent"表，检查屏幕底部的实际字样是否与表中一致；agent 升级后文案可能变化，需更新 `src/agent-status.ts` 的规则 |
| Codex 启动时提示钩子未受信任 | 重新执行安装器，它会重写 `config.toml` 中的信任条目 |

其他注意事项：

- 使用普通用户运行，避免 root。登录者能操作该服务用户有权限访问的终端和文件。
- 启动日志含完整 Token，不要公开日志、访问链接或截图。
- 默认 HTTP 不加密传输；需要加密时使用 HTTPS 代理，并正确转发 WebSocket、Host 和协议。
- Windows 用户可以在 WSL Linux 内部署（按第 1～6 节，在 Linux 内准备 Node.js、tmux 和项目依赖，避免混用 Windows 环境），也可以按第 10 节在原生 Windows 上部署。
- 服务重启通常不结束 tmux 任务；主机重启或关闭 WSL 会结束运行中的进程。可选恢复插件不能完整恢复进程内存状态。
- 上传文件默认保存在 `~/terminal-web-uploads`；下载接口可以读取服务用户有权限读取的普通文件。

## 10. 原生 Windows 部署

原生 Windows 上没有 tmux，本项目改用 **psmux**：Windows 原生的 tmux 替代品，命令和 tmux 基本一致，自带名为 `tmux.exe` 的程序。服务端代码与其他平台相同，在 Windows 上自动切换为 psmux 的用法。本节对应 `win-f-remote-hosts` 分支。

### 10.1 环境依赖

| 依赖 | 是否必需 | 说明 |
| --- | --- | --- |
| Windows 10 / 11（x64 或 arm64） | 必需 | |
| Node.js 和 npm | 必需 | 建议 Node.js 22，最低 18 |
| Git | 必需 | 用 `git@github.com:` 地址克隆需配置 SSH 密钥，否则改用 https 地址 |
| **psmux** | 必需 | **需手动下载**，不在仓库里，npm 也不会安装，见 10.2 |
| PowerShell 7（pwsh） | 建议 | 新会话默认使用；未安装时自动改用系统自带的 Windows PowerShell 5.1 |
| C++ 编译工具 / Python | **不需要** | 原因见 10.4 |

不需要安装 tmux、WSL、Cygwin 或 MSYS2。

### 10.2 下载 psmux（Windows 必需的手动步骤）

psmux 是独立的可执行程序，**不在 git 仓库中，`npm ci` 也不会安装它**，需要手动下载并放到项目目录下的 `.psmux\` 文件夹（该文件夹已在 `.gitignore` 中，不会被提交）。

1. 从 psmux 的 GitHub Releases 下载 Windows 压缩包（本项目实测版本为 v3.4.0）：
   - x64：`https://github.com/psmux/psmux/releases/download/v3.4.0/psmux-v3.4.0-windows-x64.zip`
   - arm64：同一页面的 `psmux-v3.4.0-windows-arm64.zip`
2. 在项目根目录新建 `.psmux` 文件夹，把压缩包解压进去，确保存在 `项目目录\.psmux\tmux.exe`。

在 PowerShell 中一次完成（项目根目录执行）：

```powershell
New-Item -ItemType Directory -Force .psmux | Out-Null
Invoke-WebRequest https://github.com/psmux/psmux/releases/download/v3.4.0/psmux-v3.4.0-windows-x64.zip -OutFile .psmux\psmux.zip
Expand-Archive .psmux\psmux.zip -DestinationPath .psmux -Force
Remove-Item .psmux\psmux.zip
.\.psmux\tmux.exe -V
```

最后一行输出 `tmux 3.4.0` 及 `psmux 3.4.0` 即为成功。

说明：

- 也可以用 `winget install psmux`、`scoop install psmux` 等方式装到系统里，此时不需要 `.psmux` 文件夹，但要保证服务进程的 PATH 能找到 `tmux.exe`，或用环境变量 `TMUX_BIN` 指定 `tmux.exe` 的完整路径。
- 不要让 PATH 中先出现别的 `tmux.exe`（例如 Git for Windows 或 MSYS2 自带的 tmux）。服务启动时按 PATH 顺序找第一个 `tmux.exe`；推荐的启动方式会把 `.psmux` 放在 PATH 最前面。
- 无法访问 GitHub 时，可以从已部署的机器直接复制整个 `.psmux` 文件夹。

### 10.3 获取代码与安装

```powershell
git clone --branch win-f-remote-hosts https://github.com/xutaocc/terminal-web.git
cd terminal-web
npm ci
npm run build
```

然后按 10.2 下载 psmux。实测（网络正常时）：`git clone` 约 5 秒，`npm ci` 约 6 秒（无缓存）/ 3 秒（有缓存），`npm run build` 不到 1 秒，`node_modules` 约 80 MB。

### 10.4 node-pty 是否需要编译

不需要。node-pty 是本项目唯一的原生依赖：

- 它的编译产物**不在本项目的 git 仓库里**，是 `npm ci` 时从 npm 下载的官方安装包自带的。该安装包已包含 Windows x64 / arm64 预编译好的 `conpty.node`，以及运行所需的 `OpenConsole.exe`、`conpty.dll`。
- 安装时它先检查预编译文件（安装日志显示 `Checking prebuilds...`），找到即直接使用，只把 `OpenConsole.exe`、`conpty.dll` 复制到位，**不会调用 `node-gyp` 编译**。
- 已实测：在找不到 `cl.exe`（C++ 编译器）和 Python 的环境中，`npm ci`、`npm run build` 和启动终端均成功。

仅在以下情况才会退回到本地编译、需要 C++ 编译工具：使用 32 位等预编译未覆盖的系统架构，或设置了 `npm_config_build_from_source`。

### 10.5 启动

在 Git Bash 中（项目根目录）：

```bash
PATH="$PWD/.psmux:$PATH" HOST=0.0.0.0 PORT=8090 npx tsx src/server.ts
```

在 PowerShell 中（项目根目录）：

```powershell
$env:PATH = "$PWD\.psmux;$env:PATH"; $env:HOST = '0.0.0.0'; $env:PORT = '8090'
npx tsx src/server.ts
```

启动日志会打印 Token 和各网卡的访问链接，登录与使用方式同第 4 节。Token 文件位于 `%USERPROFILE%\.config\terminal-web\auth-token`。

注意：

- Windows 上暂时不能用 `npm run dev`、`bash scripts/start.sh`、`scripts/service.sh`（依赖 bash、systemd / launchd），请按上面的命令启动。`npm start` 可用，但需先按上面设置好 PATH。
- **停止服务要结束整个进程树。** 前台运行时按 `Ctrl+C`；在后台运行时，先查到监听端口的进程号，再结束它及其子进程，否则旧的服务进程会继续占着端口，重新启动时报 `port … already in use`，而浏览器连的仍是旧代码：

  ```powershell
  netstat -ano | findstr ":8090" | findstr LISTENING     # 最后一列是进程号
  taskkill /PID <进程号> /T /F
  ```

- 停止或重启服务不会结束终端会话（psmux 会话独立运行），重新启动后浏览器刷新即可接回原会话。

### 10.6 Windows 上的行为差异

- **默认终端是 PowerShell 7**。要改用其他 shell，启动服务前设置环境变量 `TERMINAL_WEB_SHELL`（程序加参数），例如 `TERMINAL_WEB_SHELL="C:/Program Files/Git/bin/bash.exe --login -i"`。只影响新建的会话。
- 服务启动 PowerShell 时会加载 `tmux/pwsh-integration.ps1`，让侧栏、分屏和文件页能跟上 `cd` 后的目录；你自己的 PowerShell 配置文件照常加载。
- 路径显示为 `C:\...` 形式。
- psmux 的配置文件是 `tmux/web.psmux.conf`，不使用 `tmux/web.tmux.conf`。
- **会话状态钩子**：在 Windows 上，`node scripts/install-agent-hooks.mjs` 自动安装 Node 版钩子（`~/.terminal-web/agent-hook.mjs`），不需要 `curl` 或 bash，其余用法同第 8 节。安装前服务需在运行；若用 `AUTH_TOKEN` 指定了 Token，安装时用 `AUTH_TOKEN_FILE` 指向一个内容为该 Token 的文件，或用 `--url` 指定服务地址。

### 10.7 暂不支持

- 文件管理页面的「权限」操作（Windows 没有 Linux 的读写执行权限位，会提示在资源管理器中修改）；其余文件操作均可用，压缩由 `scripts/zip-manifest.ps1` 完成，不需要安装 zip。
- 后台服务安装（`scripts/service.sh`）和部署脚本（`scripts/deploy.sh`），需要时可用计划任务或 NSSM 等方式托管上面的启动命令。
- tmux-resurrect 会话快照。

### 10.8 排查

| 问题 | 检查方向 |
| --- | --- |
| 启动后新建终端失败，日志提示找不到 tmux | 确认 `.psmux\tmux.exe` 存在，且启动命令把 `.psmux` 放在了 PATH 最前面 |
| 新标签不是 PowerShell 7 | 浏览器连的可能是旧服务：确认旧进程已按 10.5 结束；或该会话是旧服务创建的，关闭后新建 |
| 重启后报 `port … already in use` | 旧服务进程没有结束，按 10.5 用 `taskkill /T /F` 结束整个进程树 |
| 局域网访问不了 | 确认启动时 `HOST=0.0.0.0`（日志中 `Listening` 一行），并检查防火墙；开着代理软件 TUN 模式时可先关闭再试 |
| 状态圆点一直灰色 | 执行 `node scripts/install-agent-hooks.mjs --check`，并重启已在运行的 Claude Code |
| `npm ci` 时出现 `node-gyp` 编译报错 | 说明没有用上预编译文件：确认系统为 x64 / arm64，且未设置 `npm_config_build_from_source` |
